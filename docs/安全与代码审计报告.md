## 一、风险总览

| 级别 | 数量 | 处理建议 |
| --- | --- | --- |
| **P0 严重** | 2 | 立即修复，其中 1 项为潜伏状态（默认关闭，开启即触发） |
| **P1 高危** | 4 | 本迭代内修复 |
| **P2 中危** | 8 | 排期修复 |

**最需要优先关注的三件事**：

1. 整页缓存会把首个游客的 `Set-Cookie` 重放给所有人 → **会话串号**（当前默认关闭，一旦后台开启即触发）

3. Xcash 支付通道、商城邀请码发货、钱包转账三处**代码路径必然报错**（引用了不存在的类 / 枚举值不匹配 / 唯一索引冲突）

## 二、P0 严重问题

### P0-1 整页缓存重放 `Set-Cookie`，导致游客会话串号

**位置**：`modules/performance/src/Http/Middleware/PerformancePageCache.php:55-59`、`46`

**问题代码**：

```php
Cache::store($store)->put($key, [
    'body'    => $response->getContent(),
    'status'  => $response->getStatusCode(),
    'headers' => $response->headers->all(),   // ← 连 Set-Cookie 一起缓存
], $ttl);

// 命中时原样重放
return new Response($cached['body'], $cached['status'], $cached['headers']);
```

**危害**：

Laravel 的 `StartSession` 与 `VerifyCsrfToken` 会在响应中下发 `Set-Cookie: <app>_session=...` 与 `Set-Cookie: XSRF-TOKEN=...`。中间件把**首个游客**的响应头整体缓存，并在 TTL（默认 3600 秒）内重放给**后续所有游客**：

- 游客 B 的浏览器写入了游客 A 的 session id → **B 直接进入 A 的会话**；若 A 之后登录，B 也变成已登录状态（账号串号）
- `XSRF-TOKEN` 与 B 自身 session 中的 token 不匹配 → B 提交任何表单（评论、注册）得到 **419 CSRF 错误**
- 这是典型的「缓存逐响应头」错误，`Set-Cookie` 属于绝对不能缓存的响应头

**触发条件**：后台「性能优化」开启 `performance_page_cache_enabled`（默认关闭，因此属于**潜伏 P0**，一旦开启立刻生效）

**修复方案**：

```php
// 只保留与内容强相关、且与用户无关的头
$headers = array_intersect_key($response->headers->all(), array_flip([
    'content-type', 'content-language', 'etag', 'last-modified', 'vary',
]));
// 绝不能包含：set-cookie、cache-control、date、age、x-ratelimit-* 等
```

同时建议补充 `X-Cache: HIT` 头便于观测，并考虑直接改用已引入的 `spatie/laravel-responsecache`（v8.4.3 已安装），它在头处理上更成熟。

### P0-2 登录/注册无限流 + 算术验证码答案空间过小 → 凭据暴力破解

**位置**：

- `routes/web.php:12-14`（登录/注册路由）
- `app/Support/Captcha.php:76-87`（算术验证码生成）

**问题代码**：

```php
// routes/web.php —— 全站唯一的 throttle 在 /email/code 上
Route::post('/login', [AuthController::class, 'login'])->name('login.store');
Route::post('/register', [RegisterController::class, 'store'])->name('user.register.store');
```

```php
// Captcha::generate()
$a = random_int(1, 9);
$b = random_int(1, 9);
// 加法：2..18（17 种结果）  减法：0..8（9 种结果）
```

**危害**：

- 全站**只有 `/email/code` 一个路由**带了 `throttle:10,1`；登录、注册、评论、签到、搜索**全部无限流**
- 算术验证码的有效答案空间 **≤ 19**，且 `verifyMath()` 用后即焚但可无限重新获取

攻击链：脚本 `GET /login` 取题 → 穷举 ≤19 个 `captcha_answer` 必然通过 → **无限次密码尝试**。注册接口同理（还能撞邮箱验证码，见 P1-1）。

**修复方案**：

```php
Route::post('/login',    [AuthController::class, 'login'])->middleware('throttle:5,1');
Route::post('/register', [RegisterController::class, 'store'])->middleware('throttle:3,1');
```

验证码改为 `-100..100` 的随机四则运算（答案空间 > 10 万），并给 `verifyMath()` 加失败计数（≥5 次强制重新出题 + 短暂锁定）。

## 三、P1 高危问题

### P1-1 邮箱验证码可被暴力枚举

**位置**：`app/Support/EmailCode.php`

**问题**：

| 项 | 现状 | 风险 |
| --- | --- | --- |
| 验证码长度 | 6 位数字 | 10⁶ 组合 |
| 有效期 | 600 秒 | 足够穷举 |
| **验证失败次数** | **无限制** | 可无限次试 |
| 绑定关系 | 不绑定会话/IP | 任何人可验证任何邮箱的码 |
| 存储形态 | **明文**存缓存 | Redis/DB 有权限者可直接读出；`cache:clear` 全丢 |

叠加 P0-2（注册无限流），10 分钟内穷举 10⁶ 完全可行 → 可用任意邮箱完成注册 / 改密。

**修复**：

- 验证失败计数：同一 key 失败 ≥5 次即作废并锁定 15 分钟
- 缓存存 `hash('sha256', $code)` 而非明文
- 验证码与发起请求的 session id 绑定
- 给 `/register`、`/email/code` 加 IP 维度限流

### P1-2 支付入账缺乏并发保护与金额校验

**位置**：

- `modules/shop/src/Services/ShopService.php:77-101`（`markPaid`）
- `modules/invite/src/Services/InviteService.php:200-216`（`markOrderPaid`）
- `modules/crypto-pay/src/Services/CoinPayService.php:266-279`（`markPaid`）
- `modules/shop/src/Http/Controllers/ShopController.php:195-230`（`notify`）

**问题**：

```php
// 三处都是同一个模式：先读后写，无锁、无条件更新
if ($order->status === 'paid') { return false; }
$order->update(['status' => 'paid', ...]);
// 然后扣库存 / 发邀请码
```

1. **并发回调重复入账**：渠道重复通知、或用户同时触发 webhook 与 PayPal 回跳，两次请求都读到 `pending`，都会执行扣库存 / 发放邀请码
2. **不校验金额**：`notify()` 验签通过即入账，未比对回调里的 `money` 与订单 `amount`
3. **通道判定取全局设置**：`notify()` 用 `SiteSettings::get('crypto_pay_channel')` 决定用哪套验签，而**不是订单自己的 `channel` 字段** → 管理员切换通道后，在途订单的回调全部失配（静默丢单）

**修复**：

```php
// 条件更新 + 判受影响行数
$affected = ShopOrder::query()
    ->whereKey($order->id)
    ->where('status', 'pending')
    ->update(['status' => 'paid', 'paid_at' => now()]);

if ($affected === 0) { return false; }   // 已被别人推进，直接返回
```

并把发货逻辑放进**同一个事务**内；`notify()` 改为按 `$order->channel` 分派验签，并校验金额一致性。

### P1-3 商城库存超卖

**位置**：`modules/shop/src/Services/ShopService.php:34-101`

**问题**：下单时只做 `if ($product->stock < 1) throw`，**不预占**。`markPaid()` 才 `where('stock','>',0)->decrementEach()`。

库存为 1 时：用户 A、B 同时下单（都通过检查）→ 各自支付 → 第一次扣减成功，第二次因 `stock > 0` 不成立而**静默跳过**，但订单照样标记 `paid` 并**调用 `deliver()` 发货**。结果是卖出了 2 份、只扣了 1 份库存，第二位买家照样拿到发货内容。

**修复**：下单时在同一事务内 `lockForUpdate()` 检查并预占库存，订单取消/超时未付时释放；`markPaid()` 用条件更新保护。

---

### P1-4 邀请码核销竞态（一枚码可注册多个账号）

**位置**：`modules/invite/src/Services/InviteService.php:58-94`

**问题**：

```php
// consume(): 先查后写，中间无锁
$invite = InviteCode::query()->where('code', $code)->where('status', 'active')->first();
if (! $invite) { return; }
$invite->forceFill(['status' => 'used', ...])->save();
```

且 `validateForRegistration()`（注册前校验）与 `consume()`（注册后核销）分处两处，中间存在 TOCTOU 窗口。两个请求并发使用同一枚邀请码时，都会读到 `status=active`，双双注册成功。

**修复**：改为原子条件更新并判断受影响行数：

```php
$affected = InviteCode::query()
    ->where('code', $code)
    ->where('status', 'active')
    ->update(['status' => 'used', 'used_by' => $userId, 'used_at' => now()]);

if ($affected === 0) { throw ValidationException::withMessages([...]); }
```

## 四、P2 中危问题

### P2-1 缓存投毒：flash 消息被固化进缓存页面

`CommentController::store()` 结束于 `redirect()->back()->with('success', '评论发表成功')`。文章详情页**不在** `PerformancePageCache::EXCLUDED_PREFIXES` 中 → 首个游客评论成功后，该 URL 的 HTML 带着 flash 进缓存，之后**所有游客访问该文章都会看到「评论发表成功」**。

同源问题：任何向可缓存页面 `redirect()->back()->with(...)` 的地方都会中招。

**修复**：把文章详情等「写操作后跳转目标」路径排除出缓存；或在判断为可缓存请求时，不读取/不渲染 session flash。

---

### P2-2 Cookie 同意状态被缓存固化（合规风险）

`resources/views/app.blade.php:16`：

```php
$analyticsAllowed = ! $cookieBannerEnabled || request()->cookie('cookie_consent') === 'full';
```

模板据此决定是否注入 GA / Clarity / 百度统计 / 自定义脚本，而这个响应会被整页缓存 → **首个游客的选择被固化给所有人**。若首个游客点了「接受全部」，后续**未同意的游客也被注入统计脚本**，违反「同意前置」的合规要求（GDPR / 个人信息保护法）。

**修复**：统计脚本改为客户端按 `cookie_consent` cookie 动态注入；或把 consent 状态加入缓存键。

---

### P2-3 缓存键可被查询串无限扩张（缓存打满）

`PerformancePageCache::key()` 用 `sha256(GET|scheme://host/uri)`，**包含完整 query string**，而 `/search`、`/feed` **不在排除列表中**。攻击者请求海量 `?q=` 随机值即可写入海量缓存条目（缓存本身无容量上限，索引上限 2000 只影响 `clearAll()` 的清理能力）→ Redis 内存打满或 file 缓存 inode 爆炸。

**修复**：`/search`、`/feed` 加入排除名单；对含 query string 的 URL 一律不缓存（或白名单化允许的 query 键）。

---

### P2-4 SafeHttpClient 全局关闭 TLS 证书验证

**位置**：`app/Support/SafeHttpClient.php:99`

```php
return Http::withHeaders($headers)
    ->maxRedirects(3)
    ->withoutVerifying();   // ← MITM 风险
```

所有经此客户端的外呼（Cloudflare Turnstile `siteverify`、码支付下单等）**不校验服务器证书**。网络路径上任何能做 MITM 的位置都可伪造响应——例如把 Turnstile 的 `{"success": false}` 改成 `{"success": true}`，人机校验即被完全绕过。

SSRF 防护本身写得很好（含 DNS rebinding 二次校验、IPv6、CGNAT、TEST-NET 全覆盖），唯独这一行把它抵消了一半。

**修复**：删除 `withoutVerifying()`；确有特殊渠道需要时，改为按渠道配置开关而非常态。

---

### P2-5 后台富文本/脚本类输入未做输出清洗（存储型 XSS 面）

| 位置 | 输入源 | 现状 |
| --- | --- | --- |
| `Shop/Detail.vue:95` | 商品介绍（Filament `RichEditor`） | `v-html="product.description"`，**未过 `HtmlSanitizer`**（对比 `StaticPageController` 是做了清洗的） |
| `app.blade.php:26` | 广告平台验证代码 | `{!! $adsVerification !!}` 原样注入 `<head>` |
| `app.blade.php:64` | 自定义统计代码 | `{!! $customAnalytics !!}` 原样注入 |
| `AdSlot.vue:115` + `runScripts()` | 广告 HTML | `v-html` 且**主动重建 `<script>` 节点执行 JS** |

这些都是「管理端可信输入」的设计选择，本身可以理解。风险取决于后台权限粒度：一旦存在权限配置过宽、或任一后台账号被入侵，即为**全站存储型 XSS + 会话劫持**。

**修复**：

- 商品描述补 `HtmlSanitizer::clean()`（与单页保持一致）
- 用 Shield 收紧「广告管理 / 站点设置 / 侧边栏卡片」的写权限，仅 `super_admin` 可写
- 对执行 JS 的广告位做二次审批或加签

### P2-6 备份恢复：破坏性操作保护不足 + 凭据明文落盘

**位置**：`app/Filament/Pages/BackupManagerPage.php`

| 问题 | 说明 |
| --- | --- |
| 服务端二次确认是空壳 | `confirmRestore()` **恒返回 `true`**（184-188 行），仅依赖前端 `wire:confirm`，可被绕过 |
| 凭据明文落盘 | `writeTempCnf()` 写入 `storage/app/backups/.my.cnf.tmp`；`mkdir(0700)` 仅作用于目录，**文件自身未 chmod**；`Process` 超时抛异常时 `@unlink($cnf)` 不执行 → **明文密码残留** |
| 路径校验缺分隔符 | `guardPath()` 用 `str_starts_with($path, realpath($dir))`，未补 `DIRECTORY_SEPARATOR` → 同级目录 `backups-evil/x.sql` 可通过校验 |
| 硬编码开发机路径 | `binaryPath()` 写死 `D:/laragon/bin/mysql/*/bin/`（Windows + Laragon） |
| shell 拼接 | `--databases '.$database` 未加引号，库名含空格即失败（源自 config，注入风险低） |
| 恢复前不备份 | 直接 `mysql < dump` 覆盖生产库，无前置快照 |

**修复**：补 `DIRECTORY_SEPARATOR`；凭据文件 `chmod 0600` 并用 `try/finally` 保证清理；恢复前自动先跑一次 `backup()`；移除硬编码路径改为配置项。

### P2-7 签到 / 评论 / 搜索缺少频率限制

`POST /quest/checkin`、`POST /articles/{slug}/comments`、`GET /search` 均无 throttle。评论默认 `status = 'approved'` 直接上墙（`CommentService::store()`），配合薄弱的算术验证码 → 可被脚本刷屏。

`GET /search` 还有额外性能问题：`WHERE content LIKE '%q%'` 对 `longtext` 全表扫描，且 `mb_strlen($q) >= 2` 门槛过低。

**修复**：上述路由加 `throttle`；考虑评论默认进入待审核队列；搜索加最小词长与分页。

---

### P2-8 评论树无上限加载

**位置**：`modules/cms/src/Services/CommentService.php:64-95`

`treeFor()` 对顶层做了 `slice(0, $topLimit)`，但**子回复全量 `groupBy` 后无条数/层级上限**。热门文章评论量大时，单次响应体积与内存占用线性膨胀，是潜在的慢请求/DoS 面。

**修复**：限制每层回复条数（如 50）+ 深度（如 2 层），超出部分走「查看更多」。

## 五、P3 功能性缺陷

这一类是「代码路径必然报错或静默失效」，不修不影响安全，但会让功能看起来「莫名其妙不能用」。

| # | 问题 | 位置 | 现象 |
| --- | --- | --- | --- |
| 1 | **Xcash 通道必崩** | `CoinPayService.php:207` | 引用 `CmsPostUrlHelper::for($post)`，该类在**整个代码库中不存在** → 走 xcash 分支直接 `Error: Class not found` |
| 2 | **Xcash 回调地址错** | `CoinPayService.php:206` | 传给网关的是 `/crypto-pay/xcash/webhook`，实际注册的是 `/crypto-pay/webhook`（`CryptoPayPlugin.php:69`）→ 回调 404，只能靠轮询兜底 |
| 3 | **商城发货邀请码必失败** | `ShopService::deliverInviteCode()` | 传 `source = 'shop_purchase'`，而 `invite_codes.source` 是 `enum('admin','gold','crypto')` → MySQL 严格模式数据截断，被 try/catch 吞掉，**买家已付款但只拿到错误信息** |
| 4 | **钱包转账第二次必失败** | `WalletService::transfer():168-187` | 两笔流水 `ref_id` 固定为 `'user:{对方id}'`，撞 `wallet_ledger_idempotency` 唯一索引 → 同一对用户只能转账一次（当前无调用方，属潜伏缺陷） |
| 5 | **广告 `card` 类型前台不渲染** | `AdSlot.vue:81-117` | `Ad::TYPES` 提供 5 种，模板只有 text/image/combo/html 四个分支 → 选 `card` 的广告静默消失 |
| 6 | **商品介绍渲染错** | `ShopController::detail()` | 迁移注释写明 description 是 Markdown，控制器却原样 `v-html` 输出 → Markdown 源码直接显示（兼 P2-5） |
| 7 | **单页内容类型靠猜** | `StaticPageController.php:30` | `str_contains($content, '<')` 二选一 Markdown/HTML，正文出现 `a < b` 会被误判为 HTML 并清洗 |

## 七、做得好的地方

审计不应只挑毛病，以下实现质量较高，值得保留并在后续开发中沿用：

1. **无 SQL 注入** —— 全项目仅 2 处 `orderByRaw`/`selectRaw`，均为常量表达式，无用户输入拼接；其余全部走 Eloquent 参数化
2. **金额一律服务端取值** —— `CoinPayService::createCheckout()` 从 `crypto_post_prices` 读价，`ShopService` 从 `$product->price` 读价，**不信任任何客户端传来的金额**
3. **支付回调全部有验签** —— 8 个回调路由虽为无 CSRF 的裸注册，但各自都有签名校验（CoinPayments SDK HMAC / Xcash HMAC-SHA256 + 时间戳漂移 ±300s / 码支付 MD5 / 虎皮椒 MD5），且统一使用 `hash_equals()` 防时序攻击
4. **SSRF 防护扎实** —— `SafeHttpClient` 覆盖 scheme 白名单、域名白名单、DNS 解析后 IP 二次校验（防 rebinding）、IPv6 展开、CGNAT/TEST-NET/组播/保留段全覆盖
5. **输出清洗到位** —— 文章正文走 symfony/html-sanitizer 白名单 + 协议白名单 + 强制 `rel="noopener noreferrer nofollow"`；评论与个人简介走 CommonMark `html_input => 'escape'`
6. **创作中心权限校验完整** —— `AuthorController` 的 edit/update/destroy 均有 `author_id` 比对，与 `author` 中间件形成双保险
7. **钱包记账设计优秀** —— `lockForUpdate()` 行锁 + `wallet_ledger` 幂等唯一索引 + 转账按 user_id 升序加锁规避死锁
8. **签到幂等双保险** —— `quest_checkins (user_id, checkin_date)` 唯一约束 + 钱包 `ref_type/ref_id` 双保险
9. **敏感路由管控严格** —— 备份下载（`basename` + 正则强校验）、订单导出、插件打包下载均为 `super_admin` 校验；插件打包还用 `array_key_exists($pluginId, $manager->discover())` 做了白名单
10. **`SafeHttpClient` 禁止重定向跟随**（`maxRedirects(3)` 有上限）、Xcash 的 `curlRaw` 未开 `FOLLOWLOCATION` —— 都有效规避了重定向型 SSRF
